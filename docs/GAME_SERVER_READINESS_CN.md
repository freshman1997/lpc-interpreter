# 游戏服务器业务可用性评估

## 结论

当前 LPC 解释器**可以开始用于游戏服务器业务原型和脚本层验证**，但还不建议直接作为完整线上游戏服务器的唯一业务运行时。

更准确的定位是：

- 可以：规则脚本、技能/道具/任务逻辑、战斗公式、配置驱动逻辑、热更新流程试验。
- 谨慎：中等复杂度副本/活动逻辑，需要补齐宿主 API、监控和回滚机制。
- 暂不建议：承载完整线上主循环、网络 IO、数据库事务、跨服通信、强安全沙箱。

## 已具备能力

- 基础语言前端、MIR 优化和 NextVM 字节码。
- 数组、mapping、class、object 等核心数据结构。
- VS Code 插件、断点、单步、变量查看、Debug Console 输出。
- 热更新版本 pin 机制。
- 基础 GC。
- benchmark 和 profile 工具。

## 主要缺口

- **宿主 API**：游戏服务器需要 socket、timer、RPC、DB、日志、配置、随机种子、时间轮等接口。
- **沙箱和权限**：需要限制脚本可调用 efun、资源配额、模块访问权限。
- **错误隔离**：脚本异常应能隔离到对象/请求/玩家维度，而不是影响整个进程。
- **资源治理**：需要执行步数限制、内存限制、单次 tick 时间限制。
- **生产观测**：需要结构化日志、profile 采样、慢脚本告警、热更新审计。
- **兼容策略**：热更新后对象字段迁移、旧版本帧退出策略、失败回滚流程还需要更多实战测试。
- **并发模型**：当前 VM 更像单线程同步解释器；多线程/协程/actor 模型需要宿主层设计。

## 推荐落地路径

1. 先把 LPC 用作“可热更新规则脚本层”，不要直接承载网络主循环。
2. 在 C++/主服务器里提供稳定 efun：
   - `log_info/log_error`
   - `call_later/cancel_timer`
   - `emit_event`
   - `db_get/db_set` 或异步请求包装
   - `send_to_player/broadcast`
3. 给每次脚本调用加预算：
   - 最大指令数
   - 最大分配数
   - 最大 wall time
4. 为热更新建立流程：
   - 编译
   - verifier
   - smoke test
   - prepare
   - activate
   - 失败回滚
5. 先选低风险业务试点，例如活动奖励计算、掉落表、任务条件判断。

## 当前不宜踩的坑

- 不要在全局变量初始化里写复杂逻辑；放到 `main()` 或业务初始化函数。
- 不要让 LPC 直接操作数据库事务；用宿主层封装幂等 API。
- 不要让脚本无限循环；上线前必须有执行预算。
- 不要把热更新当成完全无风险；必须保留旧版本和回滚路径。
